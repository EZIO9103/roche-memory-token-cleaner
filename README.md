# 记忆低Token清理器

> Roche 事实记忆整理插件。  
> 用来压缩过长记忆、清理流水账、合并已经闭环的事件线，并通过短关键词增强召回。  
> 当前说明按 **v3.5.5** 编写。

---

## 适合解决什么问题

Roche 的长期事实记忆如果长期不整理，容易出现这些情况：

- 单条记忆过长，占用大量上下文。
- 多个时间点堆在一张卡里，像聊天流水账。
- 同一个事件被拆成很多碎片，后续召回混乱。
- 旧剧情已经结束，但仍以高清细节长期占位。
- 关键词太泛，向量检索时不容易召回真正需要的记忆。
- 群聊无法自动出现在会话列表里，需要手动填写 `conversationId / groupId`。

这个插件的目标不是“删除一切旧记忆”，而是让事实记忆更像人脑记住的事件：  
**短、清楚、有后果、方便召回。**

↓

## 功能总览

| 功能 | 用途 | 风险 |
|---|---|---|
| 清理新增 | 只处理新增/变动事实，适合日常维护 | 低 |
| 大清洗 | 全量审查事实记忆，可能压缩、拆分、合并或删除 | 中 |
| 压缩过长/流水账 | 只处理“压缩候选”，偏保守 | 低 |
| 旧记忆归档 | 把较早事实压成阶段记忆，模拟人脑遗忘 | 中 |
| 修复记忆顺序 | 按 `when` 修正事实记忆排序 | 中 |
| 合并已选 | 手动选择多张结果卡，合并成一条闭环事实 | 低-中 |
| 应用全部结果 | 真正写回 Roche 事实记忆 | 需要确认 |

## 推荐使用流程

### 日常维护

适合每天或每几天整理一次。

```text
重新读取记忆
→ 清理新增
→ 查看/编辑结果
→ 必要时手动改几条
→ 应用全部结果
```

### 只处理过长记忆

适合不想动全库，只想压缩明显臃肿的卡片。

```text
重新读取记忆
→ 压缩过长/流水账
→ 查看/编辑结果
→ 应用全部结果
```

### 重度整理

适合旧记忆已经很多、顺序乱、重复多的时候。

```text
重新读取记忆
→ 大清洗
→ 查看/编辑结果
→ 合并已选 / AI压短 / 保留原文 / 删除这条
→ 应用全部结果
→ 必要时再点修复记忆顺序
```

### 整理很旧的剧情

适合剧情已经进入新阶段，早期细节不需要高清保留。

```text
重新读取记忆
→ 旧记忆归档
→ 检查归档结果
→ 应用全部结果
```

## 状态栏是什么意思

| 状态 | 含义 |
|---|---|
| 事实记忆 | 当前读取到的 Fact Memory 数量 |
| 新增/变动 | 插件判断自上次清理后新增或变动的记忆 |
| 压缩候选 | 本地规则判断偏长、像流水账或多事件的候选 |
| 估算 token | 粗略估算当前事实记忆占用 |
| AI 结果 | 当前结果区里 AI 生成的处理方案数量 |
| 需处理 | AI 或插件认为需要人工看一眼的结果 |

“压缩候选”不是必须删除，也不是新增数量。  
它只是提示：这些记忆可能值得压短或优化。

---

## 结果区怎么用

插件不会在 AI 生成结果后立刻写回 Roche。  
你看到的是一组**待确认草稿**。

常见按钮：

| 操作 | 含义 |
|---|---|
| AI重改 | 让 AI 重新处理这一张结果卡 |
| AI压短 | 在当前结果基础上继续压缩 |
| 改为单条压缩 | 把拆分/删除建议改成单条压缩 |
| 保留原文 | 不应用 AI 修改，保留原始记忆 |
| 删除这条 | 标记这条事实记忆为删除 |
| 撤销 | 撤销当前手动标记 |
| 合并选择 | 勾选这张结果卡，准备和其他卡合并 |
| 合并已选 | 把已勾选的多张卡合成一条 MERGE_REPLACE 草稿 |
| 应用全部结果 | 真正写回 Roche 事实记忆 |

## 合并已选

当多条事实记忆属于同一条已经结束的事件线时，可以使用合并功能。

例如：

```text
A：Ranni 因琐事拉黑 Ghost。
B：Ghost 改用短信继续沟通。
C：次日两人澄清误解。
```

可以勾选这些结果卡，点击：

```text
合并已选
```

插件会让 AI 生成一条初步优化后的合并草稿，而不是把原文直接拼在一起。

合并成功后：

- 被选中的旧结果卡会从当前结果区移除。
- 新增一张 `MERGE_REPLACE` 合并卡。
- 合并不会立刻写回 Roche。
- 你仍然可以继续手动编辑或 AI 压短。
- 只有点击“应用全部结果”后，才会真正写回事实记忆。

合并后的 `when` 会按所有来源重新计算：

| 来源情况 | 合并后的 when |
|---|---|
| 都是同一天 | 单日 |
| 跨天 | 起点 -> 终点 |
| 全部明确 UTC | UTC 范围 |
| 混合/未标注 | 日期级范围，不强行补 UTC |

## 各设置具体解释

### 单条最大中文字数

这是本地判断“这条记忆可能太长”的阈值。  
不是硬性截断线，也不是 AI 必须压到这个数以下。

如果设得太低，很多正常记忆都会被标为压缩候选。  
如果设得太高，流水账可能不容易被抓出来。

推荐：

```text
普通使用：180
想保留更多细节：220
想强力压缩：140-160
```

---

### 偏好最短字数 / 偏好最长字数

这两个决定 AI 压缩时的大致目标区间。

它们不是绝对限制，而是告诉 AI：  
普通事实记忆应该压到多短比较合适。

推荐不要把最短字数设太低。  
太低容易让 AI 只留下标题，丢掉“为什么重要”。

---

### 重大节点最长字数

有些事实不是普通日常，比如：

- 第一次明确关系边界
- 重要冲突与和解
- 承诺、离别、同居、称呼权限
- 长期关系转折

这种节点允许比普通事实更长。  
否则压得太短，会丢掉后续 RP 最需要召回的关系后果。

---

### 关键词数量上限

控制每条事实后面最多写几个 tag。

关键词不是剧情总结，而是检索钩子。

好的关键词：

```text
#Si称呼
#专属权限
#短信沟通
#误解纠正
```

不好的关键词：

```text
#Ranni第一次叫GhostSi并得到OnlyYou专属权限
#关系
#情绪
#未来
```

中文关键词通常 **2-6 个汉字**。  
英文关键词通常 **1-4 个词，最多 5 个词**。  
禁止整句 tag。

---

### AI批量审查条数

这是每次交给 AI 审查的记忆数量。

默认是 `1`，原因是最稳。  
批量越大，AI 越容易：

- JSON 格式出错
- 混淆不同记忆
- 把不该合并的内容合并
- 丢掉某条细节

如果你追求稳定，不建议调高。

---

### 读取长期记忆上限

插件每次读取 Fact Memory 时的上限。

如果你的角色事实记忆非常多，默认 300 可能只读到一部分。  
可以适当调高，但读取和处理都会变慢。

---

### 旧记忆归档条数

旧记忆归档会从最旧的事实里取一批，尝试整理成阶段记忆。

这个数越大，一次归档越重。  
如果你只是测试，建议先设 5。  
如果已经很熟悉插件，可以设 10-20。

## 高级开关详细解释

### 全部执行AI建议

开启后，插件会更少要求你逐条确认。

适合：

```text
你已经测试过这个角色的清理效果
你准备快速维护一批低风险记忆
你愿意在结果区大致扫一眼后直接应用
```

不适合：

```text
第一次清洗这个角色
正在处理很重要的关系节点
AI 经常把你的记忆理解错
```

---

### 关键词写回主记忆

开启后，插件会把关键词写在事实正文末尾，例如：

```text
Ranni因琐事拉黑并辱骂Ghost后，Ghost改用短信保持沟通；次日两人澄清误解，关系从冲突转回可沟通状态。 #拉黑 #短信沟通 #误解纠正
```

好处是：

- 提高关键词召回概率
- 后续向量检索更容易抓到关键物品、称呼、边界、承诺
- 对 Roche 这种轻量记忆系统更实用

如果你不喜欢正文里出现 tag，可以关闭。

---

### UTC时间模式

这个开关只处理插件自己的时间写法。

原则：

- 来源或 `when` 明确带 UTC，才保留 UTC。
- 旧记忆没有标注时区，不会强行当成 UTC。
- 不会把本地时间和 UTC 时间乱减。
- 不会自动把所有时间转换成 UTC。

如果 Roche 自己已经支持 UTC / 系统时间自选，这个开关通常不用特别担心。  
它主要是为了避免旧记忆被错误精算。

---

### Tag英文优先

关闭时：

```text
中文、英文、中英混合都允许。
插件会根据原记忆语言和召回效果自然选择。
```

开启时：

```text
关键词优先使用英文自然短语。
英文 tag 允许空格，不使用下划线。
```

例如：

```text
#Si nickname
#Only you
#private permission
```

不会写成：

```text
#Si_nickname
#Only_you
#private_permission
```

如果你的角色主要用英文对话，建议开启。  
如果中英混合较多，可以关闭，让插件自动混用。

---

### 显示Core Memory

开启后可以显示 Core Memory，方便查看。  
插件不会修改 Core Memory。

这个插件主要处理的是 Fact Memory。

## 记忆写法规则

### WHAT 正文

`WHAT` 只写事件正文，不重复结构字段。

不要写成：

```text
Ranni, Ghost: 2026-06-06, Ranni第一次叫Ghost“Si”……
```

应该写成：

```text
Ranni第一次叫Ghost“Si”，Ghost要求她再叫一次，并说“Only you”，明确这个称呼只对她开放。
```

原则：

- `who / when / where / how` 放结构字段里。
- `WHAT` 不要重复人物列表和日期。
- 单日事件不重复日期。
- 跨天事件也不要用日期范围开头，因为时间范围已经在 `when` 里。
- 跨天推进可以用“次日、随后、后来、最终”等相对顺序词。
- 分钟级时间通常不写进 WHAT，除非它是约定、航班、见面、离开等必须召回的节点。

---

### WHEN 时间

`when` 负责排序和时间范围。

可以是：

```text
2026-06-06
2026-06-06 -> 2026-06-08
2026-07-06 22:58 UTC -> 2026-07-08 00:08 UTC
```

不应该写：

```text
六月里
离港前后
上中下旬
那段时间
```

这些可以出现在正文里，但不应该出现在 `when` 字段。

---

### WHERE 地点

地点不是必填项。

线上聊天不要自动补：

```text
香港
伦敦
格鲁吉亚
```

只有原文明确地点，或地点是事件核心，才写地点。

可以写：

```text
逸东酒店
药房秤
Ranni公寓
阳台窗锁
```

---

### TAG 关键词

关键词是检索钩子，不是剧情总结。

规则：

- 中文 tag：通常 2-6 个汉字，最多 6 字。
- 英文 tag：通常 1-4 个词，最多 5 个词。
- 禁止整句 tag。
- 禁止泛词：关系、情绪、未来、地点、聊天、事件。
- 地点 tag 不是必填。
- 过短或过泛的词要组合成具体钩子。

好的例子：

```text
#Si称呼
#专属权限
#短信沟通
#误解纠正
#药房秤
#猫砂
```

英文例子：

```text
#Si nickname
#Only you
#private permission
#SMS contact
#weight dispute
#cat litter
```

## 注意事项

### 插件不会自动变聪明

AI 结果仍然需要人类判断。  
尤其是大清洗、旧记忆归档、删除建议，建议至少快速看一遍。

---

### 不建议一次处理太多

如果角色记忆很大，不建议第一次就：

```text
大清洗全部
→ 旧记忆归档很多条
→ 直接应用全部
```

更稳的方式是分批：

```text
先压缩候选
再大清洗
最后旧记忆归档
```

---

### 删除是高风险操作

删除后如果 Roche 没有额外备份，通常无法靠插件恢复。  
不确定时，优先选择压缩或保留。

---

### 合并不是归档

合并已选适合：

```text
几条卡片属于同一个已经闭环的事件线。
```

旧记忆归档适合：

```text
很早以前的一批事实已经不需要高清细节，只需要阶段性记忆。
```

二者不是同一个功能。

## 常见问题

### Q：压缩候选是什么意思？

它是本地规则判断出的候选。  
通常是偏长、像流水账或包含多个事件的事实记忆。

它不代表必须删除，也不代表一定有问题。

---

### Q：为什么我明明清洗过，还是有压缩候选？

因为压缩候选只是粗筛。  
一条记忆即使已经被整理过，只要仍然比较长或包含多个推进词，就可能被再次标记。

这不是错误，只是提示它“值得再看一眼”。

---

### Q：清理新增为什么显示 0？

说明插件判断自上次记录后没有新增或变动事实。  
这时点“清理新增”通常没有意义。

可以改用：

```text
压缩过长/流水账
```

或：

```text
大清洗
```

---

### Q：合并已选会不会立刻改我的记忆？

不会。  
合并已选只修改当前结果区草稿。  
真正写回 Roche 要等你点击“应用全部结果”。

---

### Q：为什么合并后旧卡片消失了？

这是正常行为。  
被合并的旧草稿会从结果区移除，变成一张新的 `MERGE_REPLACE` 合并草稿。

最终应用时：

```text
第一条来源记忆 → update 成合并文本
其余来源记忆 → delete
```

---

### Q：为什么不推荐 raw GitHub 链接？

`raw.githubusercontent.com` 适合临时查看源码，不适合多人长期拉取插件。  
多人安装、频繁刷新或自动拉取时，可能遇到 GitHub 429 限流。

推荐使用 GitHub Pages 地址：

```text
https://ezio9103.github.io/roche-memory-token-cleaner/manifest.json
```
